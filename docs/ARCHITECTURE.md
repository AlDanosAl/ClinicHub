# Архитектура цифровой системы клиники «Регеника»

> Живой документ. Меняется только вместе с записью в `docs/decisions/` (почему поменяли).
> Последнее обновление: 2026-10-16. Авторы: Свят, AlDanosAl, Claude.

## 0. Короткая версия

Мы строим **одну систему, а не два проекта**. Её ядро называется **ClinicHub** (уже существующий репозиторий). Он вырастает из «программы для SMS-рассылки» в **коммуникационный хаб клиники**. К ядру подключаются:

- **каналы доставки личных сообщений**: свои SIM-телефоны (SMS), боты в Telegram / ВКонтакте / MAX, при необходимости SMS-агрегатор;
- **медиаканалы клиники**: группа ВК, каналы ВК / TG / MAX. Туда публикуются посты, оттуда собирается статистика и обратная связь;
- **сайт клиники**: продающая публичная часть, кабинет пациента и веб-админка;
- **внешние системы**: МИС (выбираем), Dikidi (пока основной журнал записи), ПроДокторов (через МИС), Google-таблица с архивом пациентов (разовый и повторяемый импорт).

Всё работает **на физическом сервере в клинике**. В интернет наружу смотрит только сайт, через защищённый туннель. Персональные данные из клиники никуда не уезжают, кроме зашифрованных резервных копий.

```
           Интернет                               │              Клиника (LAN)
                                                  │
 Пациент ──► сайт (через туннель) ───────────────┼──► ClinicHub сервер ──► PostgreSQL
 TG / VK / MAX ◄──► боты (long-poll, исходящие) ◄─┼──┤   (ядро + сайт + боты)
 Группа/каналы ◄──► публикация, сбор статистики ◄─┼──┤
 МИС (облако) ◄──► адаптер МИС ◄──────────────────┼──┤        ▲
 ПроДокторов ◄── (через МИС) ──► МИС              │          │ LAN
                                                  │   Android-телефоны с SIM (SmsAgent)
```

Полная схема модулей и интеграций лежит в `docs/diagrams/system.md`.

## 1. Цели и не-цели

**Цели**
1. Персональная связь с пациентом по удобному ему каналу и с его согласия: напоминания о визите, поздравления, повторные приглашения, сбор отзывов.
2. Массовые (маркетинговые) рассылки по сегментам с учётом согласий и отписок.
3. Единая точка публикации контента во все медиаканалы клиники, сбор статистики и комментариев в одном месте.
4. Продающий сайт с онлайн-записью и кабинетом пациента.
5. Одна база пациентов, а не пять несогласованных: таблица + Dikidi + бумажные карты + МИС + сайт.

**Не-цели (сознательно не делаем)**
- Не пишем свою МИС: медкарты, ЕГИСЗ, протоколы осмотров, документы. Это делает купленная МИС.
- Не строим собственную рекламную сеть и не покупаем «серые» SIM для спама.
- Не храним медицинские сведения (диагнозы, процедуры по существу) в хабе сверх того, что нужно для коммуникаций. Минимизация данных.

## 2. Источник правды по данным

Самое важное архитектурное решение проекта ([ADR-0002](decisions/0002-master-data.md)).

| Данные | Мастер-система | Остальные |
|---|---|---|
| Пациент (ФИО, телефон, дата рождения) | **МИС** после её внедрения; до этого — **ClinicHub** | ClinicHub хранит копию + `MisPatientId` |
| Запись на приём, расписание врачей, услуги, цены | **МИС** (до внедрения — Dikidi) | сайт и боты читают через адаптер |
| Медкарта, процедуры, документы | **МИС** | хаб не хранит |
| Согласия на рассылку по каналам, отписки | **ClinicHub** | МИС может дублировать флаг |
| Привязка мессенджеров (tg/vk/max id) | **ClinicHub** | — |
| Посты, публикации, метрики, комментарии | **ClinicHub** (модуль «Контент») | соцсети — источник метрик |
| История отправленных сообщений | **ClinicHub** | — |

**Переходный период (до МИС):** ClinicHub является мастером пациентов. Google-таблица импортируется в него, а Dikidi читается только как «журнал записи». При внедрении МИС пациенты из ClinicHub выгружаются в МИС (почти у всех МИС есть импорт из Excel), после чего направление синхронизации переворачивается.

## 3. Модули

Один бэкенд-процесс ASP.NET Core (модульный монолит), одна БД. Модули разделены по папкам и namespace'ам и общаются через интерфейсы и доменные события внутри процесса. Микросервисы для клиники такого размера дадут только лишнюю сложность.

```
ClinicHub.sln
├── ClinicHub.Core              — сущности, DTO, общие интерфейсы (есть)
├── ClinicHub.Api               — хост: эндпоинты, фоновые воркеры, БД (есть → растёт)
│   ├── Modules/Patients        — пациенты, сегменты, импорт, дедупликация
│   ├── Modules/Consents        — согласия и отписки (юридически значимый журнал)
│   ├── Modules/Messaging       — кампании, шаблоны, очередь, маршрутизация по каналам
│   │     └── Channels/         — SimGateway, Telegram, Vk, Max, SmsAggregator, Email
│   ├── Modules/Content         — посты, варианты под площадки, публикации, метрики, inbox
│   ├── Modules/Integrations    — адаптеры: МИС, Dikidi, Google Sheets
│   └── Modules/Identity        — сотрудники, роли, пациенты (вход по коду), аудит
├── ClinicHub.Web               — сайт: публичные страницы + кабинет + веб-админка (новый)
├── ClinicHub.SmsAgent          — Android-приложение SIM-шлюза (есть)
└── ClinicHub.Admin             — MAUI-админка (есть; замораживается, см. ADR-0005)
```

### 3.1 Patients — пациенты и импорт
- Сущность `Patient` расширяется: `MisPatientId`, `Source` (Sheets / Dikidi / Site / Manual / MIS), `PhoneE164` (нормализованный), `Gender`, `PreferredChannel`, `Tags`, `LastVisitAt`, `IsDeleted` (мягкое удаление), `MergedIntoId`.
- **Импорт Google-таблицы**: через Google Sheets API (сервисный аккаунт с доступом на чтение к одной таблице) или через выгрузку CSV.
  1. Строки попадают в staging-таблицу `ImportRow` с исходными значениями.
  2. Нормализация: телефон в E.164, ФИО по частям, дата рождения из любых форматов.
  3. Поиск дублей: точное совпадение телефона, затем нечёткое совпадение ФИО + даты рождения.
  4. Экран «спорные строки» в админке: объединить / создать нового / пропустить.
  5. Повторный импорт идемпотентен: ключ — номер строки + хэш содержимого.
- **Сегменты**: сохранённые фильтры (давно не были, день рождения в этом месяце, делали процедуру X — когда появится МИС, теги).

### 3.2 Consents — согласия
Отдельный модуль, потому что за ошибки здесь штрафуют.
- `Consent { PatientId, Purpose (Service|Marketing), Channel (Sms|Telegram|Vk|Max|Email|Any), Granted, Source (бумажная форма/сайт/бот/устно-администратор), EvidenceRef (скан/ID записи), At, By }` — **append-only журнал**, текущее состояние вычисляется.
- **Сервисные** сообщения (напоминание о записи, перенос, результат) идут без маркетингового согласия, но только по существующей записи.
- **Маркетинговые** (акции, поздравления со скидкой, «давно не были») отправляются **только при явном предварительном согласии** на этот канал. Это требование ст. 18 закона «О рекламе».
- Отписка работает в каждом канале: «СТОП» в SMS-ответ, кнопка в боте, переключатель в кабинете. Отписка применяется немедленно.
- Архив бумажных карт **не даёт** маркетингового согласия автоматически. Нужна новая форма согласия при следующем визите (см. PLAN, этап 0).

### 3.3 Messaging — сообщения и каналы
Сюда эволюционирует существующий код рассылок (`SmsRequest` → `Campaign`).

```csharp
public interface IDeliveryChannel
{
    ChannelKind Kind { get; }                       // Sms, Telegram, Vk, Max, Email
    bool CanReach(PatientContactInfo p);            // есть ли привязка/номер
    Task<DeliveryResult> SendAsync(OutgoingMessage m, CancellationToken ct);
}
```

- **Маршрутизация** (`ChannelRouter`): для каждого получателя по порядку проверяем:
  1. Предпочтительный канал пациента, если есть привязка и согласие.
  2. Цепочку по умолчанию, настраиваемую в админке: `Telegram → MAX → VK → SMS`. Мессенджеры бесплатны и позволяют ставить кнопки, SMS дорогие и ограничены лимитами SIM.
  3. Для критичных сервисных сообщений (напоминание за сутки) — **фоллбэк**: если сообщение не доставлено или не прочитано за N часов, дублируем по SMS.
- **Кампания** = шаблон + сегмент + расписание + цель (Service/Marketing). Модерация (Created → Approved) уже реализована в ClinicHub, её сохраняем.
- **Сценарии напоминаний от визитов** ([ADR-0008](decisions/0008-care-scenarios.md)): по завершённому визиту и его процедурам система сама планирует сообщения (контрольная явка, повтор, курс, «давно не были»). Администратор видит запланированное и может его править. Визиты пока приходят из Dikidi с подтверждением администратора, потом из МИС.
- **Шаблоны** с плейсхолдерами `{имя}`, `{дата}`, `{время}`, `{врач}`, `{ссылка_запись}` и вариантами текста под канал (в SMS коротко, в боте с кнопками).
- **Анти-спам для SIM** (уже есть: лимиты на SIM, пауза после ошибок, хэш последнего текста) дополняется:
  - **рандомизацией текста** (синонимичные варианты, перестановки), чтобы операторский фильтр не видел одинаковые сообщения;
  - **окнами тишины** (не слать с 21:00 до 9:00);
  - **прогревом новой SIM** (лимиты растут постепенно).
- **Входящие**: SmsAgent уже умеет слушать отправку. Добавляем приём входящих SMS (`SMS_RECEIVED`), чтобы ловить «СТОП», «ДА/НЕТ» на подтверждение визита и вопросы. Всё это попадает в общий inbox.

**Каналы**

| Канал | Как работает | Что умеет | Ограничения |
|---|---|---|---|
| **SimGateway** (есть) | Android-телефоны в LAN забирают задачи у сервера | SMS с номера клиники, входящие SMS | лимиты операторов, риск блокировки SIM при массовой рекламе, стоимость SMS по тарифу |
| **Telegram-бот** | Bot API, long polling (исходящее соединение, белый IP не нужен) | кнопки (подтвердить/перенести), привязка по номеру (`request_contact`) | бот не может написать первым: пациент должен сам нажать «Start» |
| **VK-бот сообщества** | сообщения сообщества через Bots Long Poll API | то же, кнопки | писать можно только тем, кто разрешил сообщения сообществу |
| **MAX-бот** | Bot API MAX | кнопки, рассылки подписчикам | организация должна быть верифицирована (юрлицо/ИП РФ, через Госуслуги или СберБизнес ID) |
| **SMS-агрегатор** (опц.) | HTTP API агрегатора | буквенное имя отправителя «Regenika» | деньги за каждое SMS, регистрация имени; держим как резерв |
| **Email** (опц.) | SMTP | документы, рекомендации после визита | низкая открываемость |

**Привязка мессенджера к пациенту**: на сайте, в SMS или на ресепшене даём deep-link `t.me/RegenikaBot?start=<одноразовый токен>`. Токен связывает чат с `PatientId`. В Telegram дополнительно можно попросить поделиться номером: если он совпал с номером в базе, привязка готова.

### 3.4 Content — посты и медиаканалы
Задача: «не все посты для группы подходят для канала и наоборот».

```
Post (идея/материал)                 — тема, рубрика, текст-основа, медиа, цель (охват/запись/доверие)
 └── PostVariant (под тип площадки)  — текст и медиа, адаптированные под формат:
       ├── VkWall      (лонгрид, до 10 вложений, хэштеги)
       ├── TgChannel   (подпись к медиа до 1024 символов / текст до 4096, разметка)
       ├── MaxChannel
       └── VkChannel
 └── Publication                     — куда (конкретный канал), когда, статус, внешний id
       └── MetricSnapshot            — время, просмотры, реакции, комментарии, репосты
       └── Comment                   — в общий inbox, с возможностью ответа из админки
```

- **Матрица допустимости**: у каждого канала есть разрешённые **рубрики**. Например, «акция» идёт везде, «до/после» только в группу ВК (только с согласием пациента на публикацию фото), «новость клиники» во все каналы, «экспертный лонгрид» в ВК, а в TG — анонс со ссылкой на сайт. При планировании админка не даёт выбрать недопустимую площадку и подсказывает, какой вариант текста нужен.
- **Контент-план**: календарь с пробелами (идея из проекта «агент для постов»). Позже подключаем LLM-агента: он предлагает темы и черновики вариантов под площадки, напоминает дизайнеру сделать картинку. Человек всегда утверждает.
- **Сбор метрик**: фоновый воркер раз в N часов опрашивает API площадок по опубликованным постам: ВК (`wall.getById`, `stats.getPostReach` и т.п.), TG (просмотры поста доступны боту-админу канала через обновления; полноценная статистика у Telegram ограничена — уточнить на этапе реализации), MAX (по документации Bot API). Данные складываются в `MetricSnapshot`, и мы видим динамику.
- **Единый inbox**: комментарии к постам, сообщения ботам и входящие SMS в одной ленте. Есть фильтры, привязка к пациенту и ответ из админки в тот же канал.
- **Юридические обязательства для постов**: в рекламе медицинских услуг обязательно предупреждение о противопоказаниях и необходимости консультации специалиста (ст. 24 закона «О рекламе»). Хаб автоматически добавляет его к постам рубрик «акция/услуга». **Маркировка интернет-рекламы (erid / ОРД)** для постов в собственных каналах — проверить с юристом до запуска.

### 3.5 Integrations — внешние системы

```csharp
public interface IBookingSource          // реализуют: MisAdapter, DikidiAdapter
{
    Task<IReadOnlyList<ExternalPatient>> GetPatientsChangedSinceAsync(DateTime since, CancellationToken ct);
    Task<IReadOnlyList<Appointment>> GetAppointmentsAsync(DateOnly from, DateOnly to, CancellationToken ct);
    Task<IReadOnlyList<Slot>> GetFreeSlotsAsync(int doctorId, int serviceId, DateOnly date, CancellationToken ct);
    Task<Appointment> BookAsync(BookingRequest r, CancellationToken ct);   // для сайта и ботов
    Task CancelAsync(string appointmentId, CancellationToken ct);
}
```

- **МИС**: конкретный адаптер пишем после выбора (см. `MIS-RESEARCH.md`). Требование к МИС: открытый API или вебхуки на записи, плюс штатная интеграция с ПроДокторов.
- **Dikidi**: **официального публичного API нет**. Есть только неофициальные обёртки, собранные реверс-инжинирингом и работающие по логину/паролю. На переходный период допустим адаптер **только на чтение** (записи → напоминания), с пониманием, что он может сломаться в любой день. Целевое решение — перенести запись в МИС и отключить Dikidi ([ADR-0004](decisions/0004-dikidi.md)).
- **ПроДокторов**: пишем к нему **напрямую ничего не нужно**. Расписание и онлайн-записи синхронизирует сама МИС (у MEDODS, Renovatio, Medmis и др. такая интеграция штатная). От нас — ссылка «оставить отзыв» в боте после визита.
- **Google Sheets**: см. 3.1.

### 3.6 Сайт (`ClinicHub.Web`)
Один проект **Blazor Web App (.NET 10)** — стек, который знают оба разработчика ([ADR-0003](decisions/0003-web-stack.md)).
- **Публичная часть**: статический SSR-рендеринг, чтобы поисковики индексировали страницы, а сами страницы были быстрыми. Разделы: главная, услуги и цены, врачи, «до/после», отзывы, акции, блог (из модуля Content), контакты, онлайн-запись.
- **Конструктор** ([ADR-0007](decisions/0007-site-constructor.md)): страницы собираются из блоков, которые хранятся в БД и редактируются в админке. Цены блоки не хранят, а берут из каталога услуг, который потом синхронизируется с МИС.
- **Онлайн-запись**: выбор услуги → врача → слота, данные берутся из `IBookingSource`. Номер подтверждается кодом по SMS (через наш SIM-шлюз) или в боте.
- **Кабинет пациента**: вход по номеру телефона и одноразовому коду, без паролей. Содержит предстоящие и прошлые визиты (из МИС), перенос и отмену, управление каналами и согласиями, привязку мессенджеров, рекомендации после визита. Позже — бонусы.
- **Веб-админка** (роли Admin / Operator / Marketing): пациенты и сегменты, кампании и согласия, контент-план и публикации, inbox, аналитика, SIM-шлюз (телефоны, SIM, балансы, логи), настройки интеграций и каналов (токены ВК/TG/MAX), пользователи и журнал аудита.
- Админка доступна только из LAN клиники или через VPN, но не из публичного интернета ([ADR-0001](decisions/0001-hosting.md)).

### 3.7 SmsAgent (Android)
Остаётся как есть, с доработками:
- приём входящих SMS и пересылка их на сервер;
- отчёт о доставке (`DELIVERED`), а не только об отправке (`SENT`);
- уровень заряда и сигнала в heartbeat, тревога в админке, если телефон «пропал»;
- работа поверх HTTPS с проверкой сертификата сервера (сейчас HTTP).

## 4. Развёртывание

Подробно в [ADR-0001](decisions/0001-hosting.md).

```
┌─────────────── Клиника ────────────────────────────────────────────┐
│  Сервер-хаб (мини-ПК или выделенный ПК, Windows/Linux, ИБП)        │
│   ├── ClinicHub.Api + ClinicHub.Web  (служба / Docker)             │
│   ├── PostgreSQL                                                    │
│   ├── туннель-клиент (исходящее соединение к реле)                 │
│   └── агент бэкапа (шифрованные копии → вне клиники)               │
│  Android-телефоны с SIM ── Wi-Fi ──┘                               │
│  ПК администратора: браузер → веб-админка                          │
└────────────────────────────────────────────────────────────────────┘
          │ исходящее TLS-соединение
          ▼
  Реле в РФ (дешёвый VPS или белый IP провайдера клиники)
  — только проксирует HTTPS сайта, данных не хранит, заменяется за час
```

- **Первый этап (разработка/пилот)**: можно запускать на ноутбуке разработчика, но **только с тестовыми/обезличенными данными**. Реальная база пациентов живёт в клинике с первого дня боевой работы.
- **Внешний доступ к сайту**: (а) статический белый IP у провайдера клиники + проброс 443 на сервер, либо (б) обратный туннель через реле, которое данных не хранит (`frp`/`rathole`/WireGuard + nginx). Если реле пропадёт, теряется только доступ к сайту: данные и рассылки внутри клиники продолжают работать.
- **Боты** работают через long polling, то есть исходящими запросами. Белый IP и туннель им не нужны.
- **БД**: PostgreSQL вместо LocalDB. LocalDB предназначена для разработки и не работает как служба ([ADR-0006](decisions/0006-database.md)).
- **Бэкапы (3-2-1)**: ежедневный `pg_dump`, шифрование (age/gpg), одна копия на внешний диск в клинике, одна вне клиники (например, домашний NAS ответственного; данные зашифрованы, ключ хранится отдельно). Раз в месяц проводится пробное восстановление.
- **Защита**: шифрование диска (BitLocker/LUKS), TLS везде (и для телефонов), сотрудники входят с 2FA, журнал аудита доступа к карточкам пациентов, секреты в переменных окружения или user-secrets, а не в `appsettings.json`.
- **Электропитание и сеть**: ИБП для сервера и роутера. Телефоны-шлюзы держим на зарядке, батарея ограничивается через настройки (защита от вздутия).

| Согласие на сайт-формы | чекбокс + ссылка на политику, журнал в Consents | Web |
| Закон «О рекламе», ст. 18 | маркетинговые рассылки только по предварительному согласию; отписка | Consents + Messaging |

## 6. Нефункциональные требования
- Нагрузка: единицы тысяч пациентов, сотни сообщений в день. Хватит мини-ПК с 8–16 ГБ ОЗУ и SSD.
- Доступность сайта: «рабочие часы + лучшее усилие». Внутренние функции не зависят от интернета.
- Время восстановления после поломки сервера: не более 1 рабочего дня (сценарий проверен по бэкапу).
- Все тексты интерфейса на русском, время хранится в UTC, показывается в Europe/Moscow.
