# ADR-0009. На этапе разработки — SQL Server, переход на PostgreSQL перед продом

- Статус: **принято** (2026-10-17, решение Свята)
- Откладывает: [ADR-0006](0006-database.md) (PostgreSQL). Его выбор для прода остаётся в силе, но переход делаем позже.

## Контекст
ADR-0006 предлагал перейти с LocalDB на PostgreSQL сразу. Но на ноутбуке Свята уже работает SQL Server, а ставить туда ещё и PostgreSQL тяжело и сейчас не нужно. Боевых данных пока нет, сервер в клинике ещё не развёрнут.
Главная проблема LocalDB была в том, что она не работает как служба. Для разработки это не мешает, а полноценный экземпляр SQL Server (Express или Developer) службой работает.

## Решение
- **Сейчас** сервер (`ClinicHub.Api`) и сайт (`ClinicHub.Web`) работают на **SQL Server** через `Microsoft.EntityFrameworkCore.SqlServer`.
  - У Свята — экземпляр SQL Server на ноутбуке.
  - У AlDanosAl — любой SQL Server: Express, Developer или LocalDB.
  - Строка подключения `ConnectionStrings:ClinicHub` у каждого своя, через user-secrets, в git не попадает.
- **Перед продом** (до установки сервера в клинике и до появления реальных данных) переходим на PostgreSQL по ADR-0006: подключаем Npgsql и пересоздаём миграции одной `InitialCreate`. Окончательный выбор СУБД для прода делаем тогда же. SQL Server Express на сервере клиники тоже допустим, если так будет проще.
- **Чтобы переход был дешёвым, код пишем переносимо:**
  - никакого сырого SQL и специфичных для провайдера функций в запросах (только LINQ);
  - JSON (данные блоков сайта, настройки) храним в обычной текстовой колонке (`string` + сериализация в коде), а не в `jsonb` или `nvarchar(max)` с JSON-функциями SQL Server;
  - всё время храним в UTC (конвертер `UtcDateTimeConverter`), календарные даты — в колонке `date`;
  - схемы (`site`, `catalog`) поддерживают обе СУБД, их используем как в ADR-0007 и ADR-0008;
  - длины строк задаём явно (`HasMaxLength`).
- Существующие миграции SQL Server не удаляем: на машинах разработчиков уже могут быть базы с тестовыми данными. Изменения схемы добавляем новыми миграциями.

## Последствия
- Задача PLAN 1.1 меняется: вместо перехода на PostgreSQL остаются вынос секретов из конфигов, отказ от пароля админа по умолчанию и хранение времени в UTC. Ветку `feature/api-postgres` AlDanosAl переделывает под SQL Server.
- Перед продом появляется отдельная задача: переход на PostgreSQL (PLAN 1.13). Её цена зависит от того, соблюдались ли правила переносимости выше.
- Установщику сайта (`deploy/web`) СУБД пока не нужна. Когда сайт перейдёт на БД (PLAN 4.6), для показа в клинике хватит SQL Server Express.
