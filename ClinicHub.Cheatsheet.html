1. Назначение и цели

Система обеспечивает приём заявок на отправку SMS (как персональных — запись на приём, так и массовых — рассылка многим пациентам) и их автоматическую, безопасную отправку через дежурные телефоны с сим-картами, с учётом лимитов операторов и остатков SMS на каждой сим-карте.

Основные цели:

  • исключить ручной ввод SMS по одному — всё от пользователя идёт через одну форму;
  • не допустить блокировки сим-карт операторами из-за резких массовых отправок — сервер сам распределяет отправку по интервалам;
  • вести учёт остатков SMS по каждой SIM и не допускать отправки «в минус»;
  • отправлять SMS, когда телефон заблокирован/в фоне.

3. Функциональные требования

3.1 Типы заявок (Request)

ТипОписаниеПример
ПерсональнаяSMS одному конкретному пациенту/клиенту, подтверждение записи. Одна заявка → одно SMS (может быть из нескольких сегментов)«Уважаемый Иван, ваша запись к терапевту 12.09 в 14:00»
МассоваяОдна заявка → SMS многим абонентам. Списком получателей или по выборке из справочника«Вакцинация от гриппа доступна с 20.09, запись по телефону…»

Статусы заявки: Created (создана) → Approved (одобрена) → Scheduled (в плане) → Sending (идёт отправка) → Sent (отправлена) / Partial (частично) / Failed (ошибка) / Rejected (отклонена).

3.2 Планирование отправки REQ-SCHED

Для каждой одобренной заявки задаётся один из режимов отправки:

РежимЧто делает система
Сейчас кнопка «Отправить сейчас»Нажата после одобрения → заявка сразу попадает в очередь и уходит ближайшей партией по правилам интервалов
За деньОтправка планируется за сутки (например, за 24 часа до времени приёма/события)
За часОтправка планируется за 1 час до события
За 2 неделиОтправка планируется за 14 дней до события (напоминание/анонс)
Произвольная дата/времяАдминистратор указывает конкретный момент отправки

Важно: расписание (за день / за час / за 2 недели) означает, что система сама, в рассчитанный момент, превращает заявку в очередь отправки — без повторных действий оператора. Кнопка «Сейчас» лишь немедленно запускает уже одобренную заявку.

3.3 Подсистема планирования и «защита от блокировки» SIM REQ-RATE

Сервер (не телефоны) решает, когда и с какой номер/телефона уйдёт каждое SMS.

  • Для каждого режима отправки задаётся окно отправки (например, «в течение дня, с 9:00 до 20:00»), внутри которого сервер разносит SMS.
  • Для каждой SIM задаются лимиты: максимум SMS в минуту, в час, в сутки — пороги настраиваются (зависят от оператора).
  • Сервер строит очередь SMS и растягивает её по интервалам: если заявка на 500 SMS, а лимит 60/час — отправка займёт ~8-9 часов с паузами.
  • Очередь распределяется между всеми доступными телефонами, учитывая их лимиты и остатки.
  • Если ни одна SIM не может отправить сейчас (лимит/остаток исчерпан) — SMS остаётся в очереди с нужным приоритетом, и система отправляет позже; в журнале появляется пометка причины задержки.
  • Сервер не превышает лимиты даже при скоплении очереди — приоритет безопасности сим-карты выше скорости рассылки.

Настройки лимитов и окон хранятся в БД и могут различаться для разных SIM (разные операторы).

3.4 Управление телефонами и SIM REQ-PHONES

  • Система ведёт реестр дежурных телефонов: имя, статус (онлайн/офлайн), зарегистрированное приложение SmsAgent.
  • Телефон считается онлайн, если SmsAgent периодически (непрерывно, интервал ~10-30 c) подтверждает серверу своё присутствие.
  • Для каждого телефона ведётся список сим-карт: номер, оператор, лимиты, остаток SMS, статус.
  • Если телефон офлайн — его SIM исключаются из распределения; нагрузку берут остальные.
  • Администратор может временно заблокировать телефон или SIM (например, SIM «улетела в бан»), и сервер перестанет назначать на неё отправки.

3.5 Остатки и расчёт SMS REQ-BALANCE

Учёт длины SMS: одно «сообщение» = одно реальное SMS по тарифу оператора. Длина формирует число сегментов:

Кодировка1 SMSСоставное (многоблочное), каждый блок
GSM-7 (латиница/стандарт)до 160 символовдо 153 символов на блок
Юникод (кириллица и пр.)до 70 символовдо 67 символов на блок

Расчёт сервером: для каждого текста сервер считает число SMS-сегментов (с учётом кириллицы/юникода) и списывает именно их с остатка SIM перед назначением на отправку.

  • Ввод/коррекция остатков производится администратором в Admin (вручную, т.к. операторы не дают API) — поле «Текущий остаток», истории изменений.
  • После фактической отправки SmsAgent сообщает результат; сервер списывает фактическое число сегментов.
  • Если остатка не хватает — часть сообщений не назначается и ждёт пополнения; в журнале фиксируется причина.
  • На каждую SIM ведётся история расхода (дата, заявка, сегментов, остаток после).

Пример: массовая заявка, 120 получателей, текст 150 симв. на кириллице → 150/67 = 3 сегмента на абонента → всего 360 сегментов. Система проверит остатки всех SIM и распределит 360 сегментов по телефонам в пределах лимитов/остатков.

3.6 Фоновая работа SmsAgent на Android REQ-BG

  • Приложение работает как Android Foreground Service (постоянное уведомление «SmsAgent активен») — система Android не «усыпляет» его.
  • Работает при заблокированном экране и когда свернуто в фон.
  • Циклически (интервал настраивается, ~10-30 c) опрашивает сервер: «есть ли задачи для телефона X?»
  • При получении задачи: проверяет наличие SMS-разрешений → отправляет → сообщает серверу результат (успех/сегменты/ошибка).
  • При сбоях (нет сети, нет разрешений, телефон офлайн) — повторные попытки с нарастающей паузой, все факты пишутся на сервер.
  • Освобождение: если у телефона несколько SIM — номер SIM выбирается сервером заранее и передаётся в задаче, SmsAgent отправляет с указанной SIM (через настройки/выбор слота, где возможно).
  • Приложение отображает статус: зарегистрировано, «слушает», сколько отправил сегодня, остатки SIM (данные с сервера).

Требуемые Android-разрешения: SEND_SMS (с Android 11 — READ_PHONE_STATE/выбор SIM по возможности), INTERNET, POST_NOTIFICATIONS, работать поверх блокировки (FOREGROUND_SERVICE). Выдача/настройка разрешений документируется для оператора.

9. Интеграция с сайтом клиники

  • Весь обмен — по REST/JSON через открытые ручки /api/webhook/….
  • Сайт может создавать заявки (запись к врачу, перенос, напоминания за время) — без участия оператора кладет их в ту же систему статусов и планирования.
  • Сайт может узнавать статусы своих заявок и получать уведомление о доставке/ошибке через callback.
  • Ключ интеграции (клиника ↔ Api) настраивается отдельно, чтобы сайт не имел доступа к административным ручкам.
  • Зарезервированы поля ExternalId (id заявки на сайте) — для сопоставления заявок между сайтом и системой.

10. Нефункциональные требования

  • БД: MS SQL Server (Express 2019+ достаточно для объёма клиники); доступ через appsettings.json (строка подключения — секрет, в User Secrets в dev).
  • Надёжность: очереди и списание остатков — атомарные операции; повторная отправка исключена даже при падении соединения (идемпотентность задач по taskId).
  • Производительность: поддержка массовой рассылки на тысячи получателей — очередь в БД, обработка по интервалам; UI Admin не блокируется созданием большой заявки.
  • Безопасность: JWT для Admin, ApiKey для телефонов, интеграционный ключ для сайта; журналирование действий администратора.
  • Мониторинг: дашборд в Admin: сколько в очереди, статусы телефонов, остатки SIM, скорость отправки сегодня, ошибки.
  • Конфигурируемость: число телефонов, лимиты, окна отправки, кодировка текста — без пересборки, параметрами в БД.
